## badger-sdk

- go get github.com/dgraph-io/badger/v4
- go install github.com/dgraph-io/badger/v4/badger@latest

## Например:
Данные нужно хранить в виде: idx → pk, pk → data, т. е. отдельно индекс и отдельно данные. Они связаны по PK.
Все они лежат в одном большом «ведре», например badger_in_memory, и разделены только префиксом типа данных:
* d — PK основной ключ сущности; сам по себе является уникальным ключом, например: d:badger_in_memory:v1:user:i=000000000010;
* x — это индекс или составной индекс для префиксного сканирования, например: x:badger_in_memory:v1:user:type=admin:office=508#i=000000000033;
* u — это уникальный индекс или составной уникальный индекс для поиска по ключу, например: u:badger_in_memory:v1:user:type=admin:office=507.

* (pk) []byte{d:badger_in_memory:v1:user:i=000000000010} : (objects) []byte{v1model.User{Id: 33, Name: "Updated User 33", Type: "admin", Office: "508"}}
* (idx) []byte{x:badger_in_memory:v1:user:type=admin:office=507#i=000000000010} : (pk) []byte{d:badger_in_memory:v1:user:i=000000000010}

Искать данные — перебором префиксов индекса через итераторы, а не по полям в данных.
Или же прямым поиском по индексу, если он уникальный — одна операция.

## Правило запоминания:
Порядок полей в ключе индекса = порядок фильтров, по которым вы будете начинать поиск.
Хотите искать сначала по office — делайте индекс, где office стоит первым.
Для поддержки разных шаблонов запросов нужны отдельные индексы (обычно 1–2 на сущность под самые частые паттерны).

## Правила формирования составных индексов для префиксного поиска:
Индекс x:badger_in_memory:v1:user:type=admin:office=507#i=000000000010.
Префиксный поиск будет работать в таком случае только так:
x:badger_in_memory:v1:user:type=admin
или так:
x:badger_in_memory:v1:user:type=admin:office=507.
Если хочется искать так: x:badger_in_memory:v1:user:office=507 — ничего не найдётся.
Для такого запроса нужно сделать отдельный индекс, где office будет первым полем префикса после обязательных полей,
например: x:badger_in_memory:v1:user:office=507:type=admin#i=000000000010.

## Правила поиска по уникальному индексу.
Если нам нужно напрямую найти x:badger_in_memory:v1:user:type=admin:office=507, но у нас есть комбинированный индекс
x:badger_in_memory:v1:user:type=admin:office=507#i=000000000010, то поиск по ключу не сработает.
Так как поиск по ключу будет работать только по полному ключу, а не по префиксу (для такого случая — префиксный поиск, описан выше).
Чтобы попасть в tx.Get, нужно сделать уникальный индекс и искать по нему; рекомендуется делать такой индекс:
u:badger_in_memory:v1:user:type=admin:office=507.
BadgerDB не умеет либо «попасть» сразу через tx.Get в ключ (если это не полный ключ), либо делать фулл-скан всех индексов в БД;
используется префиксный итератор по правильно составленным ключам (описано выше).

При вставке нужно пересоздавать все индексы, которые могут быть затронуты изменением поля/полей, и удалять старые индексы.
Считается нормой иметь 1 PK и 1–2 составных индекса на сущность, чтобы покрыть основные паттерны запросов.
